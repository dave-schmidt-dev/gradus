# Independent verification: Gradus release-preparation bridge

Scope: `app/release_prepare_bridge.py`, `app/archive-upload-ios.sh` (diff only), `app/test_gradus_release_bridge.py` (`ReleasePrepareBridgeTests`), `.release/release-adapter.json`, `app/release-testflight`, `app/release_candidate/ledger.py`, `HISTORY.md`. One targeted out-of-tree lookup into `../apple_developer/release_tools/operation_runner.py` was made to confirm how the central runner dispatches adapter operations (justified below, under Task 2).

## Task 1 — Candidate-aware preparation bridge (`release_prepare_bridge.py`)

**Requirements check.** `load_context()` (release_prepare_bridge.py:132-185) validates the manifest path against the exact Git-common-dir location, requires `formatVersion:2`, `immutable:true`, `productIdentifier`, a frozen `release` block, a 64-hex `sourceSnapshot.sha256`, semver `marketingVersion`, and a positive integer `buildNumber` matching its string form — central identity is fully re-derived and checked before anything else runs. `reconcile_assigned_candidate()` (release_prepare_bridge.py:252-335) then binds the legacy `assigned` ledger to the *exact* central-proof-reported stale predecessor (`remoteHighestMarketingVersion`/`remoteHighestBuildNumber` in `_identity_proof`, release_prepare_bridge.py:188-202) before staging its allocation file, and `execute()` (release_prepare_bridge.py:561-622) never contacts App Store Connect or uploads — `OPERATIONS` (release_prepare_bridge.py:34) has no `upload` member, and `execute()`'s only subprocess call passes `--prepare-only` (release_prepare_bridge.py:578-598).

**Clean-room verification.** Ran the five `ReleasePrepareBridgeTests` in isolation plus the full 40-test suite (`BridgeTests` + `ReleasePrepareBridgeTests`) hermetically in temp dirs — all pass. `py_compile` and `bash -n` both clean.

**Blind-spot discovery.**
- Traced the retry/idempotency invariant by hand across three scenarios (fresh assigned-legacy rollover, mid-run crash after a fresh `allocated-ios.json` is written for the *new* candidate but before the old ledger is archived, and a second `reconcile_assigned_candidate` call after the stage already moved the file). All three converge correctly: the "stage only if the live `allocated-ios.json` currently holds exactly the stale legacy tuple" guard (release_prepare_bridge.py:328-334) and the "finalize only if the archived ledger confirms `superseded`" guard (release_prepare_bridge.py:218-249) together prevent both a double-allocation and a lost stale record.
- `_identity_proof`'s `remoteHighestMarketingVersion`/`remoteHighestBuildNumber == legacy_version/legacy_build` check (release_prepare_bridge.py:296-297) is real, enforced code, but `test_rollover_refuses_nonmatching_remote_predecessor_without_mutation` only exercises a mismatch through `context.build_number` vs the identity proof's own `buildNumber` (i.e. it never reaches the legacy-ledger branch) — no regression directly forces a mismatch on the remote-highest-vs-legacy-ledger fields specifically. Low-severity test-coverage gap, not a code defect (the code path is present and correct on inspection).

## Task 2 — Routing the legacy entrypoint through the bridge (`archive-upload-ios.sh`)

**Requirements check.** The diff (archive-upload-ios.sh:1296-1305) is the only change to this file: it `exec`s `release_prepare_bridge.py --operation all` when `--prepare-only` is requested, the recursion guard `GRADUS_RELEASE_BRIDGE_ACTIVE` is unset, and `HOME`/`USER`/`LOGNAME` are all unset (the marker for "invoked by the stripped-env central adapter, not an attended shell"). This exactly matches `.release/release-adapter.json:127,145,163,181`, where all four of `production-build`/`archive`/`sign`/`artifact-verify` invoke the identical argv `["bash","app/archive-upload-ios.sh","--prepare-only"]` with `environment.inherit:false, inputs:[]`. The frozen adapter command contract is untouched (verified by `test_adapter_keeps_frozen_command_contract_while_entrypoint_routes_to_bridge`), and `upload`'s adapter entry (release-adapter.json:196-211) still runs in `mode: "credential"` through the separate `gradus-app-store-connect-bridge` consumer, not through this file.

**Clean-room verification.** `bash -n` clean; the recursion guard was exercised indirectly via the `ReleasePrepareBridgeTests` fixtures (which write ledgers/allocations the way a real `--rollover-assigned` invocation would leave them) and directly via the literal-source assertions in `test_adapter_keeps_frozen_command_contract_while_entrypoint_routes_to_bridge`.

**Blind-spot discovery (material finding).** The four adapter operations `production-build`/`archive`/`sign`/`artifact-verify` are dispatched as four *separate* subprocess launches by the central runner — confirmed by reading `../apple_developer/release_tools/operation_runner.py:420-459` (`run_operation` unconditionally calls `popen_factory(**kwargs)` per operation, with its own timeout/heartbeat/status-event lifecycle; no skip-if-already-satisfied check exists there). Because `archive-upload-ios.sh`'s new hook cannot distinguish which of the four identical-argv operations triggered it, it always execs `--operation all`, never `--operation archive`/`sign`/`artifact-verify` individually. Consequently:
- `release_prepare_bridge.py`'s own module docstring ("Only the first operation may prepare an artifact; the remaining operations inspect the same durable IPA and emit their typed proofs") does not hold for the real integration: every one of the four adapter-triggered calls runs the full `"all"` branch of `execute()` (release_prepare_bridge.py:573-601), which unconditionally re-invokes the legacy shell script's resume path (re-hashes the IPA, re-checks `git rev-parse HEAD`, re-validates producer-evidence freshness against the same 600s window) and rewrites all four proof files each time, rather than three of the four calls cheaply reading the already-prepared artifact.
- I traced this for correctness, not just efficiency: it is idempotent and safe (each redundant call correctly finds the candidate already `prepared` and skips re-archiving/re-building, per `reconcile_assigned_candidate` returning `None` once the ledger already matches the central candidate), so it does not violate the no-silent-overwrite or retry-safety requirements. But it does mean the individual `--operation archive|sign|artifact-verify` branches inside `execute()` (release_prepare_bridge.py:602-622) are unreachable from the actual shell/adapter integration and are exercised only by tests that call `PREPARE.execute()` directly, bypassing the entrypoint — a real integration-coverage gap, and a repeated-work/extra-failure-surface concern (each of the 4 calls re-runs the 600s producer-evidence freshness check) worth a follow-up, though not a violation of the stated hard requirements.

## Task 3 — Regression coverage (`test_gradus_release_bridge.py`)

**Requirements check.** `ReleasePrepareBridgeTests` covers: exact-stale-allocation archival with mutation assertions (`test_assigned_legacy_state_is_archived_only_for_exact_central_allocation`), no-mutation-on-bad-proof (`test_rollover_refuses_nonmatching_remote_predecessor_without_mutation`), stage-survives-retry-before-archive (`test_staged_exact_allocation_remains_retryable_before_ledger_archive`), the four proof shapes (`test_each_preupload_operation_emits_the_central_expected_proof`), and the frozen adapter/entrypoint contract (`test_adapter_keeps_frozen_command_contract_while_entrypoint_routes_to_bridge`). Runner injections in these tests assert `"APP_STORE_CONNECT_API_KEY" not in kwargs["env"]` (test_gradus_release_bridge.py:1371), directly confirming credential-free preparation.

**Clean-room verification.** All 5 new tests pass in isolation; the full 40-test file (old `BridgeTests` + new `ReleasePrepareBridgeTests`) passes together — no regression to existing credentialed-operation coverage.

**Blind-spot discovery.** No test exercises the real `archive-upload-ios.sh → release_prepare_bridge.py` subprocess boundary end-to-end (all `ReleasePrepareBridgeTests` call `PREPARE.execute()`/`PREPARE.reconcile_assigned_candidate()` directly); the shell-side recursion guard is only checked as literal source text, not by actually running the script under a stripped `HOME`/`USER`/`LOGNAME` environment. Given the Task 2 finding above, an end-to-end test that invokes the real entrypoint four times (once per adapter operation id) against a fixture with an assigned legacy candidate would have surfaced the "always `--operation all`" behavior directly.

## Spot-checks

1. **Central identity checked before legacy reconciliation** — confirmed: `execute()` always builds/receives a validated `CandidateContext` from `load_context()` before `reconcile_assigned_candidate()` runs.
2. **Assigned legacy candidate cannot be silently overwritten; retry cannot delete a valid archived allocation** — confirmed via code trace of `reconcile_assigned_candidate`/`_finalize_staged_allocations` across normal, crash-mid-run, and repeat-call scenarios (see Task 1 blind-spot notes).
3. **Proof fields match adapter/central expectations** — confirmed `_proof_path` filenames match `release-adapter.json`'s `evidencePaths` exactly. The `proofSchema` literal key appears only in the `production-build` proof body, not in `archive`/`sign`/`artifact-verify`; cross-checked `.release/test_release_adapter.py:159-197`, which confirms the central schema's `required` field sets do **not** include a literal `proofSchema` key in the proof body (it's an adapter-side routing field, not a payload field) — not a defect.
4. **No credentials requested/exposed; cannot upload** — confirmed: `_SECRET_NAMES` stripped from the subprocess environment (release_prepare_bridge.py:575), the legacy script never reads the three ASC variables on the `--prepare-only` path (archive-upload-ios.sh:1323-1327), and `upload` is not a member of `OPERATIONS`.
5. **Clean-room tests / static checks** — `py_compile` and `bash -n` clean; 5/5 focused tests and 40/40 full-file tests pass. No upload or live-candidate mutation was performed.

## Verdict

**PASS, with one material finding for follow-up (not a hard-requirement violation).** The bridge correctly re-derives and validates central candidate identity before any legacy-state reconciliation, safely stages and finalizes exactly the stale assigned-candidate allocation with no path that can silently overwrite or lose it under retry, never requests or exposes App Store Connect credentials, and never uploads. All in-scope tests pass and no source files were modified during this review.

The one finding worth follow-up: because `archive-upload-ios.sh`'s new hook cannot distinguish which of the four identically-argv'd adapter operations (`production-build`/`archive`/`sign`/`artifact-verify`) invoked it, every one of the four resolves to `--operation all`, so the "prepare once, then just inspect" design documented in `release_prepare_bridge.py`'s module docstring is not what actually runs — all four calls re-run the legacy script's resume-validation path and rewrite all four proofs. This is idempotent and safe (confirmed by trace and by the passing test suite) but is repeated work, an extra failure surface (the 600s producer-evidence freshness window is re-checked four times instead of once), and leaves the single-operation branches of `execute()` reachable only from direct unit tests, not from the real integration.
